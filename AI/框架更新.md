# 框架更新

框架更新是用户主动触发的独立操作，不属于初始化、查询、记录或日常维护流程。

- 没有用户明确要求时，不检查模板版本，不提示或执行升级。
- 用户明确要求更新后，先完整读取模板 `main` 分支最新的 `UPDATE.md`，以它作为本次更新的临时执行协议；本仓库旧版更新说明不能替代最新协议。
- 同时读取本仓库规则以识别附加保护；新旧保护范围取并集，无法读取最新协议时停止且不修改。
- 用户拒绝升级时，继续按当前个人仓库版本正常使用。
- 更新前展示版本差异、框架路径和受保护目录，并等待确认。
- 如果现有未提交修改阻塞更新，必须明确说明框架尚未开始更新、列出阻塞路径，并在独立的编号操作区块提供“展示并处理现有修改”和“取消本次更新”；每项都支持数字或可复制完整回复。展示差异后若建议提交，必须再次使用编号的“⚠️ 需要你确认”区块。不得使用 A/B 或含糊的“确认”“确认提交”，不得默认使用 stash 或丢弃修改。
- 更新器可以在受保护目录中仅补充缺失的 README、INDEX 和 TASKS 框架入口；同名文件存在时绝不覆盖。
- Obsidian 更新只覆盖模板管理的 `work-knowledge-navigation` CSS；`.obsidian/appearance.json` 和 `.obsidian/app.json` 仅在缺失或仍为空配置时补充，已有个人外观与应用设置必须保留。
- 更新只允许操作框架文件，必须保留旧布局内容目录、整个 `Vault/`、`AI/LOCAL.md`、`AI/写入日志.md`、`AI/写入日志/`、`.kb-role`、`.kb-layout-version` 和其他用户文件。
- 框架复制后，先用更新后的个人仓库安装脚本重新安装当前 Agent 的全局 `work-knowledge` Skill，再验证 marker 中的框架版本、独立 Skill 版本和规则哈希。Codex 必须提示新开任务，BlueCode 必须重启进程，vBuddy 必须新开会话；不得声称当前上下文已热加载。其他 Agent 跳过全局 Skill 安装。
- 更新完成后必须明确说明框架已更新但 Git 尚未记录，并把“创建框架更新的本地提交”放入回复末尾独立的编号操作区块；提交和推送分别需要再次确认。
- 框架更新不得迁移个人目录。旧库缺少 `.kb-layout-version` 时只补值 1，不得创建 Vault。完成后说明旧结构正常可用，并把“生成目录迁移预览”作为同一操作区块中的独立编号选项。用户先选择提交时，提交完成后仍须再次显示迁移；未选择不等于拒绝。
- 状态检查以及任一操作完成、失败或取消后，都重新计算更新、迁移、提交和推送等仍适用项目。选择一项不清除其他项；仅在用户明确回复 `0` 或说不需要时，当前会话停止提示。
- 更新中断后只有在再次确认且最新更新器证明全部差异均属于框架白名单时才能使用恢复开关；恢复开关不得忽略个人数据或暂存区变化。

更新器必须来自与最新 `UPDATE.md` 相同的模板版本，不得优先运行个人仓库中的旧更新器。Windows 使用模板的 `scripts/update-framework.ps1`；macOS/Linux 使用模板的 `scripts/update-framework.sh`。
